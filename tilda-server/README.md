# SolanaPay-KZ — сервер приёма оплаты для Tilda

Принимает оплату в USDC или SOL на Solana за заказ, оформленный на сайте на
платформе Tilda, с пересчётом суммы из тенге. Деньги идут напрямую с
кошелька покупателя на кошелёк продавца — сервер их не хранит и не
пересылает.

## Прежде чем начинать: чего сервер никогда не попросит

**Плагин никогда не запрашивает приватные ключи — ни ваш, ни покупателя.**
Ему для работы достаточно ПУБЛИЧНОГО адреса кошелька-получателя (`recipient`
в `config.json`) — того, что вы обычно даёте, чтобы вам перевели деньги.
Приватный ключ этого кошелька не создаётся, не хранится и не запрашивается
нигде в этом проекте — ни в форме настроек, ни в письмах, ни на странице
оплаты.

Если кто-то — в переписке, в поддержке, где угодно — просит ввести
секретную фразу (seed-фразу) или приватный ключ кошелька «для настройки
приёма платежей», это мошенник. Такого шага не существует.

## Что нужно продавцу до начала

1. **Свой узел (RPC) Solana.** Публичные узлы (`https://api.devnet.solana.com`
   для тестовой сети) годятся для проверки, но ненадёжны и ограничены по
   частоте запросов для боевой работы — на mainnet нужен платный RPC-провайдер
   (Helius, QuickNode, Triton и подобные).
2. **Кошелёк-получатель.** Публичный адрес (base58), на который будут
   приходить платежи. Приватный ключ этого кошелька сервер не видит и не
   должен видеть — деньги идут напрямую с кошелька покупателя на этот адрес.
3. **Валюта магазина — тенге (KZT).** Сервер понимает только её: заказы в
   любой другой валюте отклоняются (см. `src/tilda/inbound.ts`).
4. Почта (SMTP), на которую сервер будет слать вам письма о новых и
   просроченных заказах.
5. Свободный сервер или виртуальная машина с Docker и доменом/поддоменом,
   на который уже выпущен TLS-сертификат (см. «Развёртывание» ниже — в этом
   проекте это `pay.kabyldau.digital`).

## Развёртывание

Сервер живёт как отдельный контейнер Docker, рядом с любыми другими
сервисами на том же хосте (в этом проекте — рядом с демо-магазином
`../demo-shop`), не пересекаясь с ними ни сетью, ни томами.

```bash
cd tilda-server

# 1. Настройки — из примера, свой файл. config.json в .gitignore, в репозиторий не попадает.
cp config.example.json config.json
# заполнить config.json (см. следующий раздел)
chmod 600 config.json   # только владелец файла может его прочитать

# 2. nginx — из примера, под свой домен (если ещё не сделано).
sudo cp nginx.example.conf /etc/nginx/sites-available/pay.kabyldau.digital
sudo ln -s /etc/nginx/sites-available/pay.kabyldau.digital /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

# 3. Сертификат (если ещё не выпущен).
sudo certbot --nginx -d pay.kabyldau.digital

# 4. Сборка и запуск.
docker compose up -d --build
docker compose logs -f
```

Контейнер работает в обычной (не host) сети Docker, со своей выделенной
подсетью моста (`172.21.0.0/24`, см. `docker-compose.yml`) — порт публикуется
наружу ТОЛЬКО на `127.0.0.1` хоста (`ports: "127.0.0.1:8081:8081"`), как и у
демо-магазина рядом. Единственное, что из-за этого нужно донастроить: счётчик
попыток входа в `/admin` доверяет заголовку `X-Forwarded-For` только с
адресов из `config.json` → `trustedProxyAddresses` (по умолчанию — только
loopback), а запрос от nginx до процесса внутри этой сети моста приходит с
адреса шлюза моста, а не с `127.0.0.1`. Для подсети `172.21.0.0/24` шлюз —
`172.21.0.1`; впишите его в `trustedProxyAddresses` (пример уже в
`config.example.json`). Если меняете подсеть в `docker-compose.yml` — не
забудьте поменять и адрес шлюза в `config.json`.

## Заполнение config.json

Полный список полей и их формат — в `config.example.json` (каждое поле там
с комментарием). Коротко про то, что легко перепутать:

| Поле | Что туда идёт |
|---|---|
| `recipient` | публичный адрес кошелька-получателя (не приватный ключ!). Сервер откажется запускаться, если здесь известный системный адрес Solana (System Program, Token Program и подобные) или адрес из одного повторённого символа — платёж на такой адрес пропал бы безвозвратно |
| `rpcUrl` | адрес узла Solana, обязательно `https://` |
| `cluster` | `devnet` для проверки, `mainnet` для боевой работы |
| `orderSecret` | секрет для проверки подписи заказа — придумайте сами, не короче 8 символов, впишите точно то же значение в настройки интеграции Tilda (см. ниже) |
| `notifySecret` | ОТДЕЛЬНЫЙ секрет для подписи уведомлений — не тот же, что `orderSecret` |
| `tildaNotifyUrl` | адрес, который САМА Tilda покажет вам после сохранения интеграции — см. следующий раздел |
| `publicUrl` | публичный адрес самого этого сервера, `https://pay.kabyldau.digital` |
| `adminPassword` | пароль входа в список заказов (`/admin`) |
| `merchantEmail` | куда слать письма о заказах |
| `trustedProxyAddresses` | адреса, которым доверяем заголовок `X-Forwarded-For` у `/admin` — по умолчанию только loopback; при развёртывании этим `docker-compose.yml` добавьте адрес шлюза моста (`172.21.0.1`, см. «Развёртывание» выше) |

Секреты (`orderSecret`, `notifySecret`, `adminPassword`, `smtp.pass`) можно
сгенерировать, например, командой `openssl rand -hex 24`.

## Создание интеграции в Tilda

В личном кабинете Tilda: **Настройки сайта → Платежные системы →
Универсальная платежная система → Новая платежная система (для
разработчиков)**. Протокол, по которому построен этот сервер, собран из
формы этого раздела и описан в `../docs/tilda-protokol.md` — сверяйтесь по
нему, если что-то на экране Tilda изменится.

### Адреса

| Поле формы Tilda | Значение |
|---|---|
| Название | `SolanaPay-KZ` (или своё) |
| API URL | `https://pay.kabyldau.digital/tilda/pay` |
| Тестовый API URL | тот же адрес — тестовый режим различается полем `test_mode` в теле запроса, отдельного адреса не требуется |
| Валюта | `KZT` (в списке валют Tilda есть) |

Своего поля «URL для уведомлений» в этом разделе формы нет — адрес, куда
Tilda ждёт от нас уведомление об оплате, назначает сама Tilda и показывает
его ПОСЛЕ того, как вы сохраните интеграцию (выглядит примерно как
`https://tilda.cc/payment/notify/<id>`). Скопируйте показанный адрес в
`config.json` → `tildaNotifyUrl` и перезапустите сервер
(`docker compose restart`).

### Список соответствия полей

Имена параметров в этом разделе задаём мы — впишите точно так, строчными
буквами, с подчёркиванием:

| Роль поля (по Tilda) | Имя параметра (впишите так) |
|---|---|
| Номер заказа | `order_id` |
| Сумма | `amount` — в тенге (целых единицах, не в тиынах), формат: цифры и точка, до двух знаков после неё |
| Валюта | `currency` |
| Метка времени | `timestamp` — Unix-время (секунды) |
| Тестовый режим | `test_mode` — формат `1/0` |
| Описание заказа | `description`, максимальная длина — 255 |
| Состав корзины | `products` — массив в JSON (не в base64) |
| Email покупателя | `email` |
| Телефон покупателя | `phone` |
| Имя покупателя | `customer_name` |
| Страница успеха | `success_url` |
| Страница отказа | `failure_url` |
| URL уведомлений (если Tilda присылает его в заказе) | `notify_url` — сервер это поле только сверяет с `config.tildaNotifyUrl` и пишет расхождение в журнал, уведомление по нему не отправляет никогда (см. заголовок `src/tilda/inbound.ts`) |
| Подпись | `signature` |

Поля `login`, `lang`, `country`, `receipt` этот сервер не использует — можно
оставить как предлагает Tilda по умолчанию.

### Подпись — для заказа и для уведомления отдельно

Настраивается дважды: один раз для заказа (секрет — `orderSecret`), второй
раз для уведомления (галочку «использовать те же правила» — **выключить**
и указать секрет отдельно — `notifySecret`). Правило то же самое, но
**строка для подписи разная** — правка финального ревью: строка теперь
начинается с метки роли (`order` или `notify`), и эта метка — единственное,
чем отличаются два правила, кроме секрета:

- **Тип:** «Особые правила»
- **Строка** для правила заказа (секрет `orderSecret`):
  ```
  order|{{order_id}}|{{amount}}|{{currency}}|{{timestamp}}|{{test_mode}}
  ```
  и для правила уведомления (секрет `notifySecret`):
  ```
  notify|{{order_id}}|{{amount}}|{{currency}}|{{timestamp}}|{{test_mode}}
  ```
  **Почему метка роли обязательна:** раньше оба правила совпадали дословно,
  их различал только секрет — а равенство секретов ничем не было запрещено,
  кроме этой самой страницы README. Если секреты всё же совпадали
  (например, продавец не глядя скопировал одно правило в оба поля),
  подписанный заказ, который Tilda присылает через браузер покупателя,
  становился готовым уведомлением об оплате: тем же полям, с той же
  подписью, оставалось дописать `status=paid`. Метка роли делает эти две
  подписи разными независимо от настройки секретов — вторая, самостоятельная
  линия обороны сверх запрета равенства `orderSecret`/`notifySecret` в
  `loadConfig` (`src/config.ts`).
- **Исключать поля с пустыми значениями:** **выключить**. Это важно: наша
  сторона (см. `src/signature.ts`) трактует отсутствующее поле как пустую
  строку МЕЖДУ разделителями, а не как повод сдвинуть остальные поля — если
  Tilda будет вырезать пустые поля целиком, разделители разъедутся и
  подпись перестанет сходиться.
- **Алгоритм:** SHA-256
- **Секрет как ключ алгоритма (HMAC):** **включить** — обязательно, иначе
  секрет попадёт в строку как текст, а не как ключ HMAC, и наша проверка не
  примет такую подпись.
- **Секрет:** не добавлять ни первым, ни последним элементом строки — он
  уже участвует как ключ HMAC (см. пункт выше).
- **Привести к верхнему регистру:** выключить (наша сторона сравнивает без
  учёта регистра, но нижний регистр — со значением по умолчанию).
- **Итоговую подпись в base64:** выключить — используется шестнадцатеричная запись.

### Ответ на уведомление

| Поле формы Tilda | Значение |
|---|---|
| Поле признака успеха | `status` |
| Значение признака успеха | `paid` |
| Поле номера транзакции | `transaction` |
| Ответ при успехе | `OK` |
| Ответ при ошибке | `ERROR` |
| Формат JSON | выключить — сервер и Tilda обмениваются простым текстом |

## Запасной вход через вебхук формы (на случай, если платёжная интеграция ещё не одобрена)

Пока заявка на «Новую платёжную систему» не одобрена модератором Tilda (или
если по какой-то причине эта интеграция недоступна), можно принимать заказы
через ОБЫЧНУЮ форму на сайте и её вебхук — `POST /tilda/webhook` на этом же
сервере.

0. Этот вход **выключен по умолчанию** (`config.json` → `"enableFormWebhook":
   false`) — включите его явно (`true`), только если он действительно нужен:
   продавцу, который уже пользуется одобренной платёжной интеграцией, лишний
   неподписанный вход не нужен, а его адрес всё равно напечатан здесь, в
   README. Без этой настройки `POST /tilda/webhook` отвечает `404`, как
   несуществующий маршрут.
1. В настройках любой формы на сайте (например, «Быстрый заказ» или корзина):
   **Формы → Webhook**, адрес — `https://pay.kabyldau.digital/tilda/webhook`.
2. Сумма ищется в теле запроса несколькими способами по очереди (см.
   «Разбор суммы» ниже) — самый простой и надёжный: добавить в форму своё
   поле с именем переменной **`Payment`**, в него покупатель (или скрипт на
   странице) кладёт сумму заказа в тенге.
3. Сразу после сохранения адреса Tilda пришлёт проверочный запрос
   (`test=test`) и должна получить ответ `200` за пять секунд — сервер
   отвечает на него мгновенно, никаких дополнительных действий не требуется.
4. Номер заявки (`tranid`) хранится в базе с приставкой `form:` (в списке
   заказов, `/admin`, он виден как `form:482910`) — это отдельное
   пространство номеров от платёжной интеграции (`order_id`), чтобы заявка
   этого входа не могла случайно (или намеренно) занять номер будущего
   заказа платёжной интеграции.

### Разбор суммы — этот путь НЕ ПРОВЕРЕН настоящим заказом Tilda

У вебхука обычной формы, в отличие от платёжной интеграции, нет
задокументированного поля суммы вовсе — ни в справке Tilda, ни в её форме
настроек. По непроверенным сведениям вебхук КОРЗИНЫ шлёт поле `payment` —
JSON-объект с `amount` внутри (и ещё `orderid`, `products`, `delivery`), но
подтвердить это можно только настоящей заявкой, которой пока не было.
Поэтому сервер (`src/http/routes-webhook.ts`, функция `извлечьСумму`)
пробует по очереди, честно, не выдавая предположение за факт:

1. `payment` как JSON-объект с `amount` внутри (число или строка);
2. поле `Payment` (наше собственное соглашение для обычной формы);
3. `payment` как голое число (если это не JSON);
4. `amount`, `Amount`.

Если НИЧЕГО из этого не подошло — сервер не гадает дальше: отвечает `400` и
пишет в свой журнал (`docker compose logs`) ВСЁ тело запроса целиком (в нём
нет ни подписи, ни секрета — у этого входа их не бывает вовсе). После
первой же настоящей заявки, которая не прошла, откройте журнал, посмотрите,
как Tilda прислала сумму на самом деле, и при необходимости поправьте
`ВЕРОЯТНЫЕ_ПОЛЯ_СУММЫ` в коде.

### Ограничения запасного входа

У обычной формы Tilda нет понятия «подпись заказа» — этот вход **устроен
принципиально слабее** основного:

- Нечем доказать, что запрос действительно от Tilda, а не от кого-то, кто
  узнал адрес вебхука. Единственная опора — то, что адрес нигде не
  публикуется, кроме настроек формы в личном кабинете.
- Уведомлять Tilda об оплате нечем — подписать такое уведомление нечем
  (нет секрета уведомления для этой формы), поэтому заказ в самой Tilda так
  и останется «не оплачен». Продавец отслеживает оплату по списку заказов
  этого сервера (`/admin`), а не по статусу в Tilda.
- Разбор суммы (см. выше) не проверен настоящей заявкой Tilda — только
  предположениями о формате. Первую реальную заявку стоит внимательно
  сверить со списком заказов и с журналом сервера.
- Используйте его как временную меру, а не как замену одобренной интеграции.

## Проверка тестовым платежом

1. `GET https://pay.kabyldau.digital/admin` — должен спросить пароль
   (форма входа), а не показать список заказов.
2. `POST https://pay.kabyldau.digital/tilda/pay` без поля `signature` —
   должен ответить `400`.
3. В личном кабинете Tilda, после сохранения интеграции — оформите тестовый
   заказ (или отправьте тестовую форму, если используете запасной вход).
   Откройте выданную ссылку `/pay/<токен>`, оплатите по QR любым кошельком с
   тестовой сети (при `cluster: "devnet"` в `config.json`) и убедитесь, что
   заказ дошёл до состояния «оплачен» (список `/admin`), пришло письмо
   продавцу, а после успешного уведомления — до «уведомлён» (для основного
   входа; запасной вход дальше «оплачен» не идёт, см. ограничения выше).

Для проверки без реальной Tilda в этом репозитории есть `tools/fake-tilda.ts`
— имитатор, который умеет то же самое: оформить подписанный заказ на этот
сервер и принять от него уведомление. Он не подключается к серверу как
библиотека Tilda — это независимая реализация протокола для тестов (см.
`tests/e2e.test.ts`).
