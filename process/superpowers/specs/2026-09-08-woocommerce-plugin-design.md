# Плагин WooCommerce — проектное решение

Дата: 8 сентября 2026
Этап: 2 из 4 (см. `process/TODO.md`)
Статус: утверждено 8 сентября 2026

## 1. Что делает плагин

Добавляет в WooCommerce способ оплаты «USDC на Solana». Покупатель видит
QR-код, платит кошельком, заказ подтверждается автоматически.

Плагин **автономен**: работает без серверов проекта, обращаясь только к
бирже за курсом и к узлу Solana за проверкой платежа. Магазин продолжит
принимать оплату, даже если инфраструктура SolanaPay-KZ недоступна.

## 2. Границы

**Входит:** платёжный шлюз WooCommerce, страница оплаты с QR, проверка
платежа в блокчейне, настройки продавца, тестовый режим на devnet.

**Не входит:**

- работа с приватными ключами в любом виде (запрет ТЗ, п. 5.4);
- отправка транзакций — платит покупатель своим кошельком;
- возвраты средств — продавец делает их вручную из своего кошелька;
- собственные таблицы в базе — всё в метаданных заказа.

## 3. Почему не переносим код SDK механически

SDK написан на TypeScript и служит референсом логики, но прямой перенос
невозможен и местами опасен:

**Арифметика.** В JavaScript произвольная точность встроена в язык
(`BigInt`). В PHP её нет: целые 64-битные, и промежуточное произведение
переполняется. Проверено на живом контейнере — формула SDK ломается на
сумме **92 233,72 ₸**, дальше молча превращая целое в число с плавающей
точкой:

```
 92 233 ₸  -> точно
 92 234 ₸  -> ПОТЕРЯ ТОЧНОСТИ
150 000 ₸  -> ПОТЕРЯ ТОЧНОСТИ
```

Решение: вся арифметика на `bcmath`. Расширение обязательно, при его
отсутствии плагин отказывается активироваться. Молча обсчитывать продавца
на заказах дороже двухсот долларов недопустимо.

**Проверка платежа.** В SDK её делает `validateTransfer` из `@solana/pay`
— библиотека, проверенная сообществом. Для PHP такой библиотеки нет, и
проверку придётся написать самостоятельно. Это самое ответственное место
плагина, ему посвящён раздел 6.

## 4. Состав

```
plugin/
  solanapaykz.php              точка входа, проверка окружения
  includes/
    class-money.php            арифметика на bcmath
    class-rpc.php              минимальный клиент Solana JSON-RPC
    class-rates.php            курс: Binance основной, синтетика резервная
    class-quote.php            котировка и её срок жизни
    class-payment.php          ссылка Solana Pay и метка платежа
    class-verify.php           проверка платежа в блокчейне
    class-gateway.php          платёжный шлюз WooCommerce
    class-order-meta.php       чтение и запись данных заказа
    class-poller.php           опрос: AJAX и WP-Cron
  assets/
    checkout.js                опрос статуса на странице оплаты
    checkout.css
    qrcode.min.js              отрисовка QR в браузере
  languages/
```

Каждый файл занят одним делом. Классы, не зависящие от WordPress
(`money`, `rpc`, `rates`, `quote`, `payment`, `verify`), пишутся так,
чтобы их можно было протестировать без поднятия WordPress.

Зависимостей нет: ни composer, ни сторонних библиотек Solana. Плагин
ставится обычным zip-архивом. Библиотека отрисовки QR кладётся файлом в
`assets/` — она работает в браузере покупателя и к деньгам отношения не
имеет.

## 5. Поток оплаты

1. Покупатель выбирает способ оплаты и оформляет заказ.
2. `process_payment()` получает курс, создаёт котировку, генерирует метку
   платежа, сохраняет всё в метаданных заказа, ставит статус
   `pending` и возвращает переход на страницу «Спасибо за заказ».
3. Страница показывает сумму в тенге и в USDC, QR-код и обратный отсчёт.
4. `checkout.js` каждые 5 секунд опрашивает AJAX-эндпоинт; тот проверяет
   блокчейн и возвращает статус.
5. При подтверждении заказ переходит в `processing`, страница меняется на
   «Оплата получена» без перезагрузки.
6. Независимо от покупателя WP-Cron каждые 5 минут проверяет все заказы в
   статусе `pending`, созданные этим шлюзом.
7. Через 15 минут без оплаты заказ переходит в `cancelled`.
8. Отменённые заказы проверяются ещё сутки (раздел 8).

Заказ создаётся **до** показа QR намеренно: любой пришедший платёж должен
иметь к чему привязаться, даже если покупатель закроет браузер сразу после
оплаты.

## 6. Проверка платежа

Самая ответственная часть. Ошибка означает, что продавец отдаст товар за
чужой или заниженный платёж.

### 6.1. Поиск транзакции

`getSignaturesForAddress` по адресу метки, `commitment: finalized`.
Метка — случайный публичный ключ, добавленный в транзакцию как аккаунт;
средств он не касается и приватного ключа для него не существует.

### 6.2. Проверка найденной транзакции

`getTransaction` с `maxSupportedTransactionVersion: 0` и
`commitment: finalized`, затем **все** проверки ниже. Каждая обязательна;
пропуск любой означает дыру.

1. **Транзакция успешна:** `meta.err === null`. Проверено на живом
   блокчейне: в одном произвольном финализированном блоке из 48
   транзакций с USDC **20 оказались провалившимися**. Без этой проверки
   плагин принял бы неудачную транзакцию за оплату.
2. **Метка присутствует** среди `accountKeys` транзакции.
3. **Получатель верен:** среди `postTokenBalances` есть запись, где
   `mint` равен адресу USDC для текущего кластера, а `owner` равен адресу
   продавца из настроек.
4. **Сумма достаточна:** поступление считается как разница
   `post.uiTokenAmount.amount − pre.uiTokenAmount.amount` для той же
   записи. Если в `preTokenBalances` записи нет — токен-аккаунт создан
   этой же транзакцией, и предыдущий баланс считается нулём. Проверка:
   поступление **не меньше** ожидаемой суммы. Переплата допустима.

Суммы в ответе RPC приходят строками — сравнение ведётся через `bcmath`,
без преобразования в число с плавающей точкой.

### 6.3. Статусы

| Статус | Когда | Что делает плагин |
|---|---|---|
| `pending` | транзакции нет, котировка жива | продолжает опрос |
| `expired` | транзакции нет, срок вышел | переводит заказ в `cancelled` |
| `confirmed` | транзакция прошла все проверки | заказ в `processing` |
| `mismatch` | транзакция найдена, проверку не прошла | заказ в `on-hold`, заметка продавцу |

Сбой сети или RPC **не является** ни одним из этих статусов: он
пробрасывается как ошибка и не меняет состояние заказа. Временная потеря
связи не должна выглядеть ни как «покупатель не заплатил», ни как
«платёж поддельный».

## 7. Курс

Порядок как в SDK: основной источник — Binance (`USDTKZT × USDCUSDT`,
прямой пары тенге с USDC не существует), резервный — синтетика через
курс доллара от агрегатора.

Курс кешируется в транзиентах WordPress на 60 секунд — отдельно от срока
жизни котировки. В SDK эти сроки однажды оказались связаны одним
параметром, и окно ценового риска удваивалось; здесь они разведены с
самого начала.

**Если курс недоступен, заказ не создаётся.** Покупатель видит сообщение
«оплата криптовалютой временно недоступна, выберите другой способ».
Продать по выдуманному курсу хуже, чем не продать.

## 8. Платёж на отменённый заказ

Отмена заказа не отменяет QR-код: покупатель мог отсканировать его и
заплатить позже. Транзакция в блокчейне необратима.

Поэтому отменённые заказы этого шлюза проверяются ещё **24 часа** (срок
настраивается). При обнаружении платежа:

- заказ переводится в `on-hold`;
- к заказу добавляется заметка с суммой и номером транзакции;
- продавец видит уведомление в админке.

Дальше решает продавец: восстановить заказ или вернуть деньги. Молча
потерять платёж плагин не имеет права.

## 9. Настройки продавца

| Настройка | По умолчанию | Примечание |
|---|---|---|
| Включён | нет | |
| Заголовок | «Оплата криптовалютой (USDC)» | видит покупатель |
| Описание | текст про оплату кошельком | видит покупатель |
| Solana-адрес продавца | пусто | обязателен, проверяется формат |
| Кластер | devnet | переключатель тестового режима |
| Адрес RPC | пусто | обязателен, проверяется формат URL |
| Наценка, % | 0 | к сумме в тенге до конвертации |
| Срок жизни котировки | 15 минут | |
| Проверять отменённые | 24 часа | 0 отключает |

Тестовый режим существует, чтобы продавец проверил всю цепочку на
бесплатных монетах devnet, прежде чем принимать настоящие деньги.

## 10. Требования к окружению

| Что | Версия | Почему |
|---|---|---|
| WordPress | 7.0+ | WooCommerce 11 ниже не ставится (проверено) |
| WooCommerce | 9.0+ | |
| PHP | 8.1+ | |
| `bcmath` | обязательно | без него расчёт ломается на 92 233 ₸ |
| `curl` | обязательно | запросы к бирже и узлу |

При активации плагин проверяет всё перечисленное и при нехватке
отказывается включаться с понятным сообщением, называющим недостающее.

## 11. Тестирование

**Автоматически (PHPUnit, без WordPress):** арифметика, разбор ответов
курса, формирование ссылки Solana Pay и — главное — проверка платежа на
зафиксированных ответах RPC. Обязательные случаи: провалившаяся
транзакция, чужой получатель, заниженная сумма, отсутствие метки,
отсутствие записи в `preTokenBalances`, переплата.

**Вручную на демо-магазине:** сначала весь путь на devnet с бесплатными
монетами, затем один настоящий платёж на небольшую сумму в mainnet.

Фикстуры для тестов берутся из реальных ответов блокчейна, а не
придумываются: структура `postTokenBalances` уже изучена на живой
транзакции.

## 12. Чего в плагине нет

- обращений к серверам SolanaPay-KZ;
- собственных таблиц в базе;
- кода, способного распорядиться деньгами;
- зависимостей от composer.
