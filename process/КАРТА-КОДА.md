# Карта кода Core SDK

Путеводитель для чтения. Файлы перечислены в порядке, в котором их
имеет смысл читать: снизу вверх, от арифметики к публичному API.

Всего ~700 строк кода и ~1400 строк тестов в `src/` и `tests/`.

## С чего начать

`src/money.ts` (~130 строк) — арифметика денег. Самый важный файл: здесь
решается, сколько криптовалюты покупатель платит за товар в тенге.

Что смотреть: все расчёты идут на целых числах (BigInt) в минимальных
единицах токена, а не на обычных числах с плавающей точкой. Причина в
том, что `0.1 + 0.2` в JavaScript не равно `0.3`, и на деньгах такие
погрешности накапливаются молча. Округление всегда вверх, в пользу
продавца — покупатель никогда не платит меньше запрошенного.

Проверить самому: `convertKztToTokenUnits('10000', '459.60', 6)` должно
дать `21758051n`, то есть 21.758051 USDC.

## Дальше по слоям

**`src/config.ts`** (~50 строк) — адреса монет USDC в основной и тестовой
сети, сроки по умолчанию. Адреса проверены запросом к блокчейну; ошибка в
одном символе означала бы платежи в никуда.

**`src/errors.ts`** (~25 строк) — шесть типов ошибок. Разделение не
формальное: `RateSourceError` означает «источник курса подвёл, попробуй
следующий», а `ConfigError` — «данные на входе неверны, пробовать
бесполезно».

**`src/rates/`** — получение курса.
- `binance.ts` — основной источник. Курс собирается из двух тикеров,
  потому что прямой пары тенге с USDC на бирже не существует.
- `synthetic.ts` — резервный. Отдельная история: CoinGecko вообще не
  знает тенге и на запрос отвечает пустотой с кодом «успешно», поэтому
  курс собирается из двух независимых величин.
- `provider.ts` — переключение между ними и кеш. Главное правило: если
  оба источника недоступны, бросается ошибка, а не подставляется
  последний известный курс. Устаревший курс хуже явного отказа.

**`src/quote/quote.ts`** (~135 строк) — котировка. Фиксирует цену на 15
минут и замораживает объект от изменений. Смотреть на `assertValidQuote`:
котировка возвращается из базы продавца, то есть приходит извне, и
проверяется заново при каждом использовании.

**`src/payment/request.ts`** (~90 строк) — ссылка Solana Pay и QR-код.
Метка платежа — это 32 случайных байта в виде адреса; пара ключей не
создаётся, приватного ключа не существует.

**`src/verify/verify.ts`** (~135 строк) — поиск платежа в блокчейне и его
проверка. Сама сверка делегирована библиотеке `@solana/pay`: самописная
проверка входящей транзакции — место, где легче всего принять чужой
платёж. Смотреть на различение статусов: сбой связи не должен выглядеть
как «платёж не совпал».

**`src/client.ts`** (~105 строк) — публичный класс, собирающий всё вместе.
Здесь же задаётся приоритет источников курса.

## Тесты

`tests/` — 118 тестов. Читать необязательно, но `tests/money.test.ts`
полезен: в нём видно, какие граничные случаи считаются недопустимыми и
почему.

`tests/integration/devnet.test.ts` ходит в тестовую сеть Solana
по-настоящему. Запуск: `npm run test:integration`.

## Как посмотреть в работе

```bash
npm install --include=dev   # флаг обязателен: на сервере NODE_ENV=production
npm test                    # 118 тестов, без сети
npm run test:integration    # обращается к тестовой сети Solana
```

## На что обратить внимание при чтении

Три места, где ревью находило ошибки, и стоит проверить, согласен ли
ты с решениями:

1. `src/money.ts`, `applyMarkup` — наценка меньше 0.01% отвергается, а не
   округляется до нуля молча. Верхняя граница наценки — 100%.
2. `src/verify/verify.ts` — платёж, пришедший после истечения котировки,
   всё равно подтверждается: транзакцию в блокчейне отменить нельзя,
   решение принимает продавец.
3. `src/quote/quote.ts`, `assertValidQuote` — насколько строгая проверка
   котировки оправдана. Она отвергает пустые и повреждённые значения,
   но требует, чтобы продавец хранил котировку без изменений.
